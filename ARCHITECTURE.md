# Архітектура — frontend

Правила залежностей і структура папок для цього конкретного проєкту. Написано
**перед** великим рефакторингом, не після — зміни в `REFACTOR_SEO_PLAN.md`
підпорядковані цьому документу, не навпаки.

**v2 (2026-09-28).** Перша версія цього файлу мала лише `features/`, без
розрізнення entity/feature. Це виправлено: нижче — цільова картина на
5 шарів, але з явним застереженням, який з них будується **зараз**, а який
**коли з'явиться реальна складність**, а не наперед.

> Не робити архітектуру складнішою, ніж складність самого бізнесу. Почати з
> мінімуму, що реально потрібен, і додавати шар лише в момент, коли перший
> файл цього шару має що в собі містити — не раніше.

## П'ять шарів — цільова картина

```
┌─────────────────────────────────────────────┐
│  app/            маршрутизація, SEO, layout  │
└───────────────────────┬───────────────────────┘
┌───────────────────────▼───────────────────────┐
│  features/       що користувач МОЖЕ ЗРОБИТИ    │  «додати в кошик»,
│                                                │  «переглянути каталог»
└───────────────────────┬───────────────────────┘
┌───────────────────────▼───────────────────────┐
│  entities/       ЩО ЦЕ ЗА ОБ'ЄКТ               │  Product, Category,
│                                                │  Model, OrderItem
└───────────────────────┬───────────────────────┘
┌───────────────────────▼───────────────────────┐
│  application/    оркестрація use-case'ів       │  ⏳ поки НЕ будуємо
│  domain/         чисті бізнес-правила          │  ⏳ поки НЕ будуємо
└───────────────────────┬───────────────────────┘
┌───────────────────────▼───────────────────────┐
│  infrastructure/ HTTP, БД, платежі, доставка   │  lib/api/, redux/,
│                                                │  services/
└─────────────────────────────────────────────────┘
                    shared/  (нижче, для всіх)
```

**`application/` і `domain/` навмисно порожні сьогодні.** Перевірено, не
припущено: на фронтенді зараз немає жодної чистої бізнес-функції (сума
кошика, знижка, оркестрація створення замовлення) — усе або йде на бекенд
одним запитом (`createOrder(data)`), або взагалі не порахован на клієнті.
Будувати ці два шари зараз означало б порожні папки з файлом-заглушкою — саме
той premature-abstraction, проти якого застерігає власний принцип YAGNI.
Тригер на створення:

- **`domain/`** — щойно з'явиться перша чиста функція бізнес-правила, яку
  хочеться тестувати без React/API (найімовірніший перший кандидат:
  `domain/cart/calculateCartTotal.ts`, якщо підсумок кошика почне рахуватись
  на клієнті, а не лише на бекенді).
- **`application/`** — щойно use-case стане багатокроковим (перевірити кошик
  → порахувати ціну → застосувати знижку → доставка → створити замовлення →
  сповіщення). На бекенді цей момент уже настав — `orderController.js`
  (823 рядки) саме така оркестрація, і Фаза 6 `REFACTOR_SEO_PLAN.md`
  (декомпозиція на сервіси) — це і є побудова `application/`-шару, просто під
  назвою `services/`. На фронтенді поки немає багатокрокового use-case.

## Entity vs Feature — ключове розрізнення, якого не було в v1

- **Entity** відповідає на «що це за об'єкт»: `Product`, `Category`, `Model`,
  `OrderItem`. Чиста презентація об'єкта (як його показати) і його форма
  (типи) — без знання про те, в якому контексті сторінки він з'явився.
- **Feature** відповідає на «що користувач може з ним зробити»: переглянути
  каталог, додати в кошик, оформити замовлення.

Конкретний приклад із реального коду, не абстрактний: `ProductCard`
(сьогодні — `product-item.tsx`, 385 рядків, з уже задокументованим DRY-боргом
— три розкладки в одному файлі, `REFACTOR_SEO_PLAN.md` крок 4.3.3) сьогодні
використовується на сторінці категорії, сторінки моделі І сторінки пошуку —
трьох різних *фічах*. Якби він жив у `features/catalog/`, `features/search/`
довелось би імпортувати з чужої фічі, що прямо порушує правило 3 нижче. Він
належить `entities/product/ui/`, а кожна фіча його звідти імпортує.

## Структура

```
app/[locale]/(routes)/...     маршрути — тонкі композиційні корені
components/                    оболонка: Header, Footer — компонують кілька
                                features/ докупи (єдиний дозволений виняток)
components/ui/                 = "shared/ui" концептуально, фізично не
                                перейменовано (див. "Про shared/" нижче)
features/
  catalog/        перегляд/фільтр/сортування списку товарів
  product/        сторінка одного товару (не картка — сторінка цілком)
  cart/           додати/прибрати/змінити кількість
  checkout/       оформлення замовлення, доставка, оплата
  account/        логін/реєстрація/OTP, особисті дані, історія
  search/         пошук у шапці, сторінка результатів, підбір по VIN
  contacts/       форма "передзвоніть мені", сторінка контактів
entities/
  product/        { ui: ProductCard/PriceTag/StockBadge, model: типи+формат }
  category/       { ui: CategoryNav/CategoryBreadcrumb, model: типи }
  model/          { типи авто-моделі Audi }
  order-item/     { рядок товару в кошику — і в шапці, і в чекауті, і в
                    історії замовлень: та сама entity, три фічі-споживачі }
lib/, redux/, services/, i18n/   = "infrastructure" концептуально
hooks/                          РОДОВІ хуки без знання про домен
```

### Про `shared/` — не перейменовуємо `lib/`

Брифи, які лягли в основу цього документа, пропонують `shared/{ui,lib,config,
validation,types}`. Концептуально це те саме, чим уже є `lib/` +
`components/ui/` у цьому проєкті. Фізичне перейменування (`lib/api/` →
`shared/lib/api/`, `components/ui/` → `shared/ui/`) торкнулося б імпортів у
**кожному** файлі проєкту заради зміни назви папки — нуль функціональної
користі, суцільний ризик конфліктів під час паралельного рефакторингу фіч.
Рішення: **вокабуляр «shared» = `lib/` + `components/ui/` концептуально,
фізично лишаються на місці.** Якщо колись з'явиться справжня причина
фізичного перейменування — окремий коміт, ізольований від будь-якої іншої
зміни.

## Правила залежностей

1. `app/**/page.tsx` → `features/*`, `entities/*`, `components/*`, `lib/*`.
2. `components/{Header,Footer,...}` → може імпортувати кілька `features/*`.
   Фіча ніколи не імпортує назад із `components/`.
3. `features/<domain>/**` → `entities/*`, `lib/*`, `redux/<свій-слайс>`,
   `components/ui/*`, `hooks/*` (родові), `i18n/*`. **Не** імпортує з
   `features/<інший-domain>/**` напряму. Потрібна чужа фіча — питання
   зазвичай означає, що спільна частина насправді `entity`, а не `feature`
   (див. приклад із `ProductCard` вище).
4. `entities/<name>/**` → лише `lib/*`, `components/ui/*`, `i18n/*`. **Не**
   імпортує жодної `features/*` — entity не знає, в якій фічі її показують.
5. `lib/api/*`, `services/*` → нуль залежностей нагору. Ніколи не імпортують
   React-компонент, Redux, `features/*` чи `entities/*`.
6. `redux/order` (кошик) → `features/cart/*` і `components/header/*` (бейдж
   лічильника). **Не** `features/catalog/*` чи `features/product/*` — картка
   товару не працює з кошиком напряму, кличе `features/cart`'s
   `useAddToCart(productId)`.

Порушення — те саме, що дефект дизайну з `design-principles-reviewer`-класу:
не крашиться, але сповільнює наступну зміну. Ловиться рев'ю, не компілятором.

## Зовнішні провайдери (платежі, доставка) — межа вже правильна

`services/monobank.ts` і Нова Пошта — вже today ізольовані адаптери
(`REFACTOR_SEO_PLAN.md`, крок 2.9). Принцип на майбутнє: коли з'явиться
**другий** платіжний чи логістичний провайдер, тоді і тільки тоді — інтерфейс
(`PaymentProvider` з `createPayment`/`refundPayment`), і `monobank.ts`
стає однією з реалізацій, а не єдиною. Будувати інтерфейс під єдину
реалізацію — абстракція заради абстракції, YAGNI-порушення.

## Тестування, SEO, кешування, спостережуваність

Не дублюються тут — уже описані по фазах `REFACTOR_SEO_PLAN.md`:
- тести з поведінкою в одному коміті, піраміда unit→integration→e2e — Фаза 1
  і мандатне правило репозиторію;
- кеш-стратегія за доменом (каталог кешується, кошик/чекаут — ні) — Фаза 3,
  уже реалізовано для каталогу (`revalidate: 300` + теги в `lib/api/`);
- SEO (метадані, canonical, JSON-LD, структура URL) — Фаза 8;
- Fail Fast / валідація на межі — вже мандатний принцип проєкту.

Один факт — один дім: якщо ці розділи розійдуться з планом, план вважається
джерелом істини для порядку робіт, цей файл — джерелом істини для структури
папок.

## Структура однієї фічі

```
features/catalog/
  components/
    category-nav.tsx
    catalog-filters.tsx
  hooks/
    use-category-products.ts   ← useInfiniteQuery, обгортає lib/api/catalog.ts
    use-categories.ts
  types.ts                     ← типи, що не виходять за межі фічі
  index.ts                     ← публічний фасад: що можна імпортувати ззовні
```

`api/` не дублюється всередині фічі — `lib/api/*` (Фаза 2, `81aa874`) уже
доменно розділений шар даних; фіча кличе його напряму або через
`actions/get-data.ts` (server actions, викличні з клієнта).

`index.ts` — не формальність: єдиний дозволений вхід ззовні
(`import { ProductList } from "@/features/catalog"`), не пряме глибоке
посилання на внутрішній файл.

## Порядок міграції

Інкрементально, фіча за фічею, кожен крок — окремий коміт, тести зелені до
і після.

1. **`entities/product/`** — `ProductCard`/`PriceTag`/`StockBadge` (вже
   заплановано в кроках 4.3.3–4.3.6). Робиться першим, бо `features/catalog/`
   і `features/product/` обидва на нього спираються — будувати фічі до
   entity означало б переносити картку двічі.
2. **`features/catalog/`** — список товарів (`useInfiniteQuery`), дерево
   категорій (`useCategories`), фільтри/сортування/пагінація.
3. **`features/cart/`** — Redux `order` (уже ізольований) + UI кошика.
4. **Header стає оболонкою** — `components/header/` як шелл, що компонує
   `features/catalog` (каталог-дропдаун), `features/cart` (бейдж+прев'ю),
   `features/account` (логін), `features/search` (пошук),
   `features/contacts` (діалог дзвінка). Практичний приклад правила 2.
5. **`features/product/`** — сторінка товару цілком (галерея, характеристики,
   схожі товари, відгуки) — спирається на `entities/product/` з кроку 1.
6. **`features/search/`, `features/account/`, `features/checkout/`,
   `features/contacts/`** — за потреби, коли рефакторинг наступним
   торкається відповідного маршруту («touched means assessed»).

Стара плоска структура не видаляється разом — файл за файлом, у тому самому
коміті, де його вміст переїжджає. Порожні `_components/`-папки під `app/`
прибираються, коли останній файл з них переїхав.

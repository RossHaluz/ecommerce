# Архітектура — frontend

Правила залежностей і структура папок для цього конкретного проєкту. Написано
**перед** великим рефакторингом, не після — зміни в `REFACTOR_SEO_PLAN.md`
підпорядковані цьому документу, не навпаки.

Мета та сама, що й у решти рефакторингу: щоб через рік будь-хто зміг
відкрити один файл, зрозуміти його одразу, і додати наступну фічу, не
чіпаючи те, що вже працює.

## Шари

```
        ┌─────────────────────────┐
        │   app/ (маршрути)       │  page.tsx — композиційний корінь,
        │                         │  не місце для розмітки
        └────────────┬────────────┘
                      │
        ┌─────────────▼────────────┐
        │   components/ (оболонка) │  Header, Footer — компонують ФІЧІ
        └─────────────┬────────────┘  докупи; єдиний, хто може імпортувати
                      │                з кількох features/ одразу
        ┌─────────────▼────────────┐
        │   features/<domain>/     │  catalog, product, cart, checkout,
        │                         │  account, search, contacts
        └─────────────┬────────────┘
                      │
        ┌─────────────▼────────────┐
        │   lib/, redux/, i18n/    │  інфраструктура: HTTP-клієнт, типи,
        │                         │  кошик, переклади
        └───────────────────────────┘
```

Кожна стрілка — це напрям, у якому МОЖНА імпортувати. Не навпаки. `lib/api/`
ніколи не імпортує з `features/`; `features/catalog/` ніколи не імпортує з
`features/cart/`.

## Межі фіч (features/)

Мапляться на реальні маршрути `app/[locale]/(routes)/`, не вигадані наперед:

| Фіча | Маршрути, які вона обслуговує | Що всередині |
|---|---|---|
| `catalog` | `/`, `/categories`, `/categories/[categoryId]`, `/[modelName]`, `/categories/[categoryId]/[modelName]` | список товарів (нескінченний скрол), картка товару в гріді, фільтри, сортування, дерево категорій |
| `product` | `/product/[productId]` | галерея, ціна, кнопка купівлі, характеристики, схожі товари, відгуки |
| `cart` | немає власного маршруту — живе в шапці й чекауті | стан кошика (Redux `order`), іконка+прев'ю в шапці, рядок товару в кошику |
| `checkout` | `/checkout`, `/success` | форма замовлення, доставка (Нова Пошта), оплата |
| `account` | `/account` | логін/реєстрація/OTP, особисті дані, історія замовлень |
| `search` | `/search`, `/search/[modelName]` | пошук у шапці, сторінка результатів, підбір по VIN |
| `contacts` | `/contacts` | форма "передзвоніть мені", віджет контактів, сторінка контактів |

Якщо фіча ще не існує як папка — це нормально, вона з'являється в момент,
коли перший файл цього домену переноситься (крок 2 нижче).

## Структура однієї фічі

```
features/catalog/
  components/
    product-card.tsx
    product-list.tsx
    category-nav.tsx
  hooks/
    use-category-products.ts   ← useInfiniteQuery, обгортає lib/api/catalog.ts
    use-categories.ts
  types.ts                     ← типи, що не виходять за межі фічі
  index.ts                     ← публічний фасад: що можна імпортувати ззовні
```

`api/` **не дублюється** всередині фічі. `lib/api/catalog.ts`,
`lib/api/products.ts` тощо вже є доменно розділеним шаром даних (Фаза 2
рефакторингу, коміт `81aa874`) — фіча імпортує звідти напряму або через
`actions/get-data.ts` (server actions, викличні з клієнтських компонентів).
Дублювати цей шар усередину `features/*/api/` було б порушенням DRY заради
відповідності шаблону.

`index.ts` — не формальність. Це єдиний дозволений вхід ззовні: `import { ProductCard } from "@/features/catalog"`, ніколи
`import ProductCard from "@/features/catalog/components/product-card"` з іншої
фічі. Всередині самої фічі — прямі імпорти, без бар'єру.

## Що НЕ стає фічею

- **`lib/api/`** — інфраструктура. HTTP-клієнт, каталог URL, теги кешу. Про
  React, JSX і Redux не знає нічого.
- **`lib/types.ts`** — типи, спільні для 2+ фіч (`Product`, `Category`,
  `Model`, `Meta`). Тип, потрібний лише одній фічі, живе в її власному
  `types.ts`.
- **`redux/order/`** (кошик) і `redux/{customizer,scroll-up}/` (UI-стан) —
  інфраструктура стану. `redux/{categories,items,models,search}/` зникають у
  міру переходу їхніх споживачів на TanStack Query (Фаза 3.2) — вони й були
  тимчасовою заміною того, що тепер робить `features/catalog/hooks/`.
- **`components/ui/`** — дизайн-система (Button, Dialog, Input…). Не знає, що
  таке товар чи кошик.
- **`components/` (плоскі файли поза `ui/`)** — оболонка сторінки: `Header`,
  `Footer`, `ContactsWidget`, `ScrollToTop`. Єдине місце, де дозволено
  імпортувати з кількох `features/*` одночасно, бо їхня єдина робота —
  компонувати фічі в один шелл. Сама фіча ніколи не імпортує з `components/`
  у зворотному напрямку.
- **`hooks/`** (верхній рівень) — тільки родові хуки без знання про домен:
  `use-mounted`, `use-origin`, `useIsSmallScreen`. Доменний хук (`use-categories`)
  переїжджає у `features/catalog/hooks/`.
- **`app/[locale]/(routes)/`** — маршрутизація. `page.tsx` — це `generateMetadata`
  + виклик даних для метаданих + `<FeatureComponent />`. Розмітка в
  `page.tsx` не живе.

## Правила залежностей (перевіряються оком, не лінтером — поки що)

1. `app/**/page.tsx` → може імпортувати `features/*`, `components/*`, `lib/*`.
2. `components/{Header,Footer,...}` → може імпортувати кілька `features/*`.
   Жодна фіча не імпортує назад із `components/`.
3. `features/<domain>/**` → може імпортувати `lib/*`, `redux/<свій-слайс>`,
   `components/ui/*`, `hooks/*` (родові), `i18n/*`. **Не** може імпортувати
   з `features/<інший-domain>/**` напряму — тільки через `index.ts`, і тільки
   якщо це справді потрібно (найчастіше не потрібно: `product` не має знати
   про `cart`, він викликає `features/cart`'s `useAddToCart()` хук, а не лізе
   в Redux-стан кошика сам).
4. `lib/api/*` → нуль залежностей нагору. Ніколи не імпортує React-компонент,
   Redux, чи `features/*`.
5. `redux/order` (кошик) → імпортується з `features/cart/*` і з
   `components/header/*` (бейдж лічильника). **Не** з `features/catalog/*`
   чи `features/product/*` — картка товару не працює з кошиком напряму,
   вона кличе `features/cart`'s `useAddToCart(productId)`.

Порушення цих правил — те саме, що дефект дизайну з
`design-principles-reviewer`-класу: не крашиться, але робить наступну зміну
повільнішою. Ловиться рев'ю, не компілятором — поки що.

## Порядок міграції (інкрементально, фіча за фічею)

Не "перепишемо все за раз". Кожен крок — окремий коміт, зелені тести до і
після.

1. **`features/catalog/`** — перше, бо це вже в роботі (переклад
   `products.tsx` на TanStack, `useCategories`). Забирає: список товарів,
   картку товару в гріді, дерево категорій, фільтри/сортування/пагінацію.
2. **`features/cart/`** — маленька, самодостатня (Redux `order` уже ізольований).
   Потрібна для кроку 3.
3. **Header стає оболонкою.** Після 1–2 `components/header.tsx` (475 рядків)
   розбирається на `components/header/` (сам шелл: лого, розкладка,
   `<header>`-обгортка) + виклики `features/catalog` (каталог-дропдаун),
   `features/cart` (іконка+прев'ю кошика), `features/account` (логін),
   `features/search` (пошук), `features/contacts` (діалог "передзвоніть мені").
   Це і є практичний приклад правила 2 вище.
4. **`features/product/`** — сторінка товару.
5. **`features/search/`, `features/account/`, `features/checkout/`,
   `features/contacts/`** — за потреби, коли відповідний маршрут наступним
   торкається рефакторинг (той самий принцип "touched means assessed" з
   `REFACTOR_SEO_PLAN.md`).

Стара плоска структура (`components/product-item.tsx`,
`app/.../_components/*` розкидані по маршрутах) не видаляється разом —
видаляється файл за файлом, у тому самому коміті, де його вміст переїжджає
в `features/`. Порожні `_components/` папки під `app/` прибираються, коли
останній файл з них переїхав.
